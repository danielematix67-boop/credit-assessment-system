# Credit Assessment System

A rule-based credit risk assessment engine for financial positions, combining deterministic financial rule evaluation with LLM-assisted narrative reporting. Built in Python with a Streamlit front end.

The system ingests a company's financial data (a `CreditPosition`), evaluates it against a configurable set of financial and sustainability rules, classifies the overall risk status, and produces a human-readable report — generated either deterministically or by an LLM (Google Gemini or a local Ollama model), with automatic fallback to a deterministic generator if the LLM is unavailable.

## Features

- **Deterministic rule engine** — evaluates a credit position against configurable financial and sustainability rules (revenue growth, EBITDA profitability, leverage, interest coverage, etc.).
- **Configurable severity thresholds** — each rule supports multi-level severity thresholds (e.g. `MEDIUM` → `HIGH`) defined declaratively in YAML.
- **Automatic rule discovery** — rules are auto-registered via a discovery mechanism, so new rules only need to be added to the `src/rules` package and referenced in the configuration.
- **Multi-agent workflow** — the assessment pipeline is composed of independent agents (assessment → analysis → reporting), orchestrated end-to-end with per-stage timing.
- **Pluggable LLM reporting** — narrative reports can be generated by Google Gemini or a local Ollama model, with a deterministic template-based generator as a safe fallback if the LLM call fails (rate limits, timeouts, connection errors, missing model, etc. are all handled gracefully).
- **Streamlit web UI** — interactive application to input or select a demo credit position, choose a reporting mode, run an assessment, and view the resulting report.
- **Environment-aware configuration** — automatically detects whether it's running locally or on Streamlit Community Cloud and adjusts the available reporting modes accordingly (Ollama is only offered when running locally).
- **Extensive automated test suite** covering rules, services, agents, orchestration, and integration flows.

## Architecture

The system follows a layered, agent-based pipeline:

```
CreditPosition
      │
      ▼
┌─────────────────────┐
│  Assessment Service   │  → runs RuleEngine over configured rules
│  (deterministic)      │  → produces Assessment (rule results, findings, status)
└─────────┬────────────┘
          ▼
┌─────────────────────┐
│   Analysis Agent      │  → transforms Assessment into AssessmentAnalysis
└─────────┬────────────┘
          ▼
┌─────────────────────┐
│  Reporting Agent      │  → primary generator (Deterministic / Gemini / Ollama)
│                        │  → deterministic fallback on failure
└─────────┬────────────┘
          ▼
        Report
```

This is coordinated by the `AssessmentWorkflow`, which is in turn wrapped by an `AssessmentOrchestrator` exposing a single `run(position) -> Report` entry point. Each stage's elapsed time is tracked, and the reporting stage records which generator was ultimately used (`PRIMARY` or `FALLBACK`) along with any error encountered.

## Rule Engine

Rules are defined declaratively in [`config/rules.yaml`](config/rules.yaml). Each entry specifies:

| Field | Description |
|---|---|
| `rule_id` | Unique identifier (e.g. `R001`) |
| `rule_name` | Human-readable name |
| `category` | Grouping (`revenue`, `profitability`, `leverage`, `profitability_quality`, ...) |
| `threshold` | Base trigger threshold |
| `severity` | Default severity if triggered |
| `severity_direction` | `LOWER_IS_WORSE` or `HIGHER_IS_WORSE` |
| `severity_thresholds` | Optional list of `{threshold, severity}` pairs for graduated severity (e.g. `MEDIUM` at -10%, `HIGH` at -30%) |

Rules currently implemented include:

- **R001** — Revenue growth deterioration
- **R002** — Negative EBITDA
- **R003** — EBITDA margin deterioration
- **R004** — NFP / EBITDA leverage
- **R005** — Interest expense to EBITDA
- **R006** — EBITDA materially supported by finished goods inventory increase
- **R007** — Interest coverage ratio

New rules are picked up automatically: implement a `Rule` subclass under `src/rules/<category>/...`, register it, and reference its `rule_id` in `rules.yaml` — the discovery mechanism (`src/rules/discovery.py`) imports every rule module in the package at startup so the registry is always in sync with the codebase.

Rule results feed into an `AssessmentStatusCalculator`, which derives an overall `AssessmentStatus`: `NORMAL`, `ATTENTION`, or `CRITICAL`.

## Reporting Modes

The reporting stage supports three interchangeable generators, selected via the Streamlit sidebar:

| Mode | Description | Availability |
|---|---|---|
| **Deterministic** | Template-based report built directly from the rule findings, no LLM involved | Always |
| **Gemini + Fallback** | Google Gemini generates the narrative report; falls back to the deterministic generator on failure | Always (requires API key) |
| **Ollama + Fallback** | A local Ollama model generates the narrative report; falls back to the deterministic generator on failure | Local execution only |

The fallback logic (`ReportingAgent`) classifies LLM failures (rate limiting, service unavailability, connection errors, authentication issues, missing model, timeouts) into concise diagnostic messages and transparently switches to the deterministic generator, so the workflow never fails outright due to an LLM outage.

## Configuration

Depending on the reporting mode you want to use, configure the following.

### Gemini

Provide your API key either as a Streamlit secret or an environment variable:

```bash
export GEMINI_API_KEY="your-api-key"
```

Or in `.streamlit/secrets.toml`:

```toml
GEMINI_API_KEY = "your-api-key"
```

### Ollama (local only)

```bash
export OLLAMA_HOST="http://localhost:11434"   # default
export OLLAMA_MODEL="qwen3:0.6b"               # default
```

Or via `.streamlit/secrets.toml`:

```toml
[ollama]
host = "http://localhost:11434"
model = "qwen3:0.6b"
```

Ollama mode is automatically hidden when the app detects it's running on Streamlit Community Cloud.

### Rules

Rule definitions and thresholds live in `config/rules.yaml`. Edit this file to add, remove, or tune rules without touching application code.

## Usage

### Run the Streamlit app

```bash
streamlit run app/streamlit_app.py
```

This launches the web UI where you can:
1. Select or input a credit position (including pre-built demo scenarios).
2. Choose a reporting mode (Deterministic / Gemini / Ollama).
3. Run the assessment and view the generated report, along with per-stage timing and reporting provenance (which generator was actually used).

### Run programmatically

```python
from src.orchestration.orchestrator_factory import create_default_orchestrator
from src.models.position import CreditPosition

orchestrator = create_default_orchestrator()

position = CreditPosition(
    position_id="ACME-2025",
    revenue=1_000_000,
    ebitda=80_000,
    ebitda_margin=0.08,
    nfp_to_ebitda=6.2,
    # ... other financial fields
)

report = orchestrator.run(position)
print(report)
```
