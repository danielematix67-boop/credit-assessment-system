# Credit Assessment System

A modular and deterministic rule-based system for the assessment of credit positions.

The project is designed as a prototype for a **transparent, traceable and extensible credit assessment framework**, where business rules are explicitly implemented, independently testable and configurable. The architecture is intentionally separated from any natural-language generation component, allowing an LLM or other reporting layer to be integrated without delegating decision-making logic to the model.

---

## 1. Project Overview

The **Credit Assessment System** evaluates credit positions against a configurable set of financial and sustainability rules.

For each credit position, the system:

1. Loads the configured assessment rules.
2. Discovers and registers the available rule implementations.
3. Instantiates the rules from their configuration.
4. Evaluates each rule against the credit position.
5. Produces a structured `RuleResult` for every rule.
6. Aggregates the rule results into an overall assessment status.
7. Optionally generates explanatory comments through a separate comment layer.

The core assessment logic is therefore **deterministic and independent from natural-language generation**.

This separation is a fundamental architectural principle of the project:

> **Rules determine the assessment; the reporting layer explains the assessment.**

---

## 2. Design Principles

The system follows several principles aimed at ensuring maintainability, transparency and testability.

### Deterministic decision logic

Business decisions are implemented through explicit Python rules rather than generated by an LLM.

Given the same position and configuration, the system produces the same assessment.

### Separation of concerns

Each component has a clearly defined responsibility:

* **Rules** evaluate individual financial conditions.
* **Rule Engine** executes rules.
* **Rule Registry** resolves rule identifiers into rule implementations.
* **Configuration Layer** defines which rules are active and their parameters.
* **Assessment Status Calculator** aggregates rule outcomes.
* **Comment Engine** generates explanatory comments.
* **Models** represent domain objects.

### Configuration-driven execution

Rule thresholds, severities and metadata are externalized through configuration rather than hard-coded in the rule engine.

### Extensibility

New rules can be introduced without modifying the core rule engine.

A new rule only needs to implement the `Rule` interface and register itself with a unique rule identifier.

### Traceability

Every rule produces a structured result containing information such as:

* rule identifier;
* rule name;
* category;
* evaluation status;
* evaluated value;
* threshold;
* severity.

This makes the assessment process auditable and explainable.

### Testability

The system is designed around small, independently testable components.

The project currently includes a comprehensive automated test suite covering domain models, rules, discovery, configuration, registry behaviour, services and comment generation.

## 5. Rule Abstraction

All business rules inherit from the common `Rule` abstraction.

A rule receives a `RuleConfig` containing its configuration and exposes an `evaluate()` method:

```python
class Rule(ABC):

    _registry: ClassVar[dict[str, type["Rule"]]] = {}

    def __init__(self, config: RuleConfig):
        self.config = config

    @abstractmethod
    def evaluate(
        self,
        position: CreditPosition,
    ) -> RuleResult:
        pass
```

The base class also provides common result-generation functionality and handling for non-evaluable rules.

This ensures that individual rules focus exclusively on their business logic.

---

## 6. Rule Registration

Rules are dynamically registered through a decorator-based registry.

Conceptually:

```python
@Rule.register("R001")
class RevenueGrowthRule(Rule):
    ...
```

The registry maps a stable business identifier to its implementation:

```text
R001 → RevenueGrowthRule
R002 → NegativeEbitdaRule
R003 → EbitdaMarginRule
R004 → PfnToEbitdaRule
R005 → FinancialExpensesToEbitdaRule
R006 → EbitdaInventoryContributionRule
```

Duplicate rule identifiers are rejected during registration.

Unknown identifiers are also explicitly rejected when building the rule set.

---

## 7. Dynamic Rule Discovery

The system does not require the central registry to explicitly import every rule implementation.

`discover_rules()` dynamically walks the `src.rules` package and imports rule modules.

Importing a rule module triggers its registration decorator, making the rule available in the registry.

This provides a plug-in-like architecture:

```text
New rule module
       │
       ▼
Package discovery
       │
       ▼
Module import
       │
       ▼
@Rule.register(...)
       │
       ▼
Rule Registry
```

The discovery mechanism deliberately excludes infrastructure modules such as:

* `registry`;
* `discovery`;
* base rule modules.

The discovery process is also designed to be idempotent once modules have already been imported.

## 8. Rule Construction

The rule registry is responsible for transforming configuration objects into concrete rule instances.

```python
def build_rules(
    configs: list[RuleConfig],
) -> list[Rule]:

    discover_rules()

    rules = []

    for config in configs:
        rule_class = Rule.get_registered_rule(
            config.rule_id
        )
        rules.append(rule_class(config))

    return rules
```

The configuration therefore determines **which rules are instantiated and with which parameters**, while the registry determines **which implementation corresponds to each rule identifier**.

This keeps configuration and implementation decoupled.

---

## 9. Rule Engine

The `RuleEngine` deliberately contains no business-rule logic.

Its responsibility is simply to execute the supplied rules:

```python
class RuleEngine:

    def __init__(self, rules: list[Rule]):
        self.rules = rules

    def evaluate(
        self,
        position: CreditPosition,
    ) -> list[RuleResult]:

        results = []

        for rule in self.rules:
            results.append(
                rule.evaluate(position)
            )

        return results
```

This design makes the engine generic: it does not need to know whether a rule evaluates revenue growth, EBITDA, leverage or another financial indicator.

## 10. Rule Results

Every rule returns a structured `RuleResult`.

A result contains the information required to understand the outcome of an individual rule evaluation:

```text
RuleResult
├── rule_id
├── rule_name
├── category
├── status
├── value
├── threshold
└── severity
```

Typical rule statuses include:

* `TRIGGERED`
* `NOT_TRIGGERED`
* `NOT_EVALUABLE`

This structured representation allows downstream components to operate on rule outcomes without depending on the implementation details of individual rules.

---

## 11. Assessment Status

The overall assessment is derived from the individual rule results.

The current aggregation logic is:

```text
Triggered rules = 0
        │
        ▼
     NORMAL

Triggered rules = 1
        │
        ▼
    ATTENTION

Triggered rules ≥ 2
        │
        ▼
    CRITICAL
```

The `AssessmentStatusCalculator` is intentionally separated from the `RuleEngine`.

This is important because:

> **Rule evaluation and assessment aggregation are two different responsibilities.**

The rule engine determines what happened at rule level; the status calculator determines the overall assessment.

## 13. Configuration

Rules are configured independently from their implementation.

A configuration entry can define attributes such as:

```text
rule_id
rule_name
category
threshold
severity
```

This allows thresholds and metadata to be changed without modifying the rule implementation itself.

For example, the implementation of a revenue-growth rule can remain unchanged while the configured threshold is adjusted.

This approach supports:

* parameterization;
* reproducibility;
* environment-specific configurations;
* easier validation;
* reduced coupling between code and business parameters.

## 14. Comment and Reporting Layer

The comment system is deliberately separated from the assessment engine.

The intended architecture is:

```text
Credit Position
      │
      ▼
Rule Engine
      │
      ▼
Rule Results
      │
      ▼
Assessment Status
      │
      ▼
Comment / Reporting Layer
```

The comment layer can transform structured assessment results into human-readable explanations.

This separation is particularly important for future integration with an **LLM-based reporting component**.

The LLM should operate on already-determined results rather than independently deciding whether a credit rule is triggered.

Therefore:

```text
Deterministic layer
        │
        ├── evaluates rules
        ├── determines statuses
        └── determines assessment
                 │
                 ▼
       Natural-language layer
                 │
                 └── explains results
```

This preserves deterministic decision-making while allowing flexible natural-language reporting.

## 18. Extending the System

Adding a new rule follows a simple workflow.

### 1. Create the rule module

Place the implementation in the appropriate taxonomy directory.

For example:

```text
src/rules/financial/liquidity/new_rule.py
```

### 2. Implement the `Rule` interface

```python
from src.rules.base.rule import Rule


@Rule.register("R007")
class NewRule(Rule):

    def evaluate(self, position):
        ...
```

### 3. Add the rule configuration

Add the corresponding configuration entry containing the rule identifier, threshold, severity and metadata.

### 4. Add tests

Create a corresponding test module under:

```text
tests/rules/financial/liquidity/
```

### 5. Run the complete test suite

```bash
pytest
```

No modification to `RuleEngine` should be required.

This is a key characteristic of the architecture: **new business rules should be additive rather than requiring changes to the orchestration layer.**

## 19. Architectural Boundaries

The project intentionally maintains the following boundaries:

| Component                    | Responsibility                        |
| ---------------------------- | ------------------------------------- |
| `Rule`                       | Common rule abstraction and registry  |
| Individual rules             | Business-rule evaluation              |
| `RuleConfig`                 | Rule parameters and metadata          |
| `RuleConfigLoader`           | Configuration loading                 |
| `RuleConfiguration`          | Configuration source/path definition  |
| `discovery.py`               | Dynamic rule module discovery         |
| `registry.py`                | Rule construction from configuration  |
| `RuleEngine`                 | Rule execution                        |
| `RuleResult`                 | Structured rule outcome               |
| `AssessmentStatusCalculator` | Overall assessment aggregation        |
| `AssessmentService`          | Assessment orchestration              |
| `CommentEngine`              | Human-readable explanation generation |
| LLM layer                    | Optional natural-language reporting   |

Keeping these boundaries explicit reduces coupling and makes the system easier to validate and evolve.

## 21. Architectural Goal

The long-term goal is to provide a credit assessment framework that is:

**Deterministic**
The same inputs and configuration produce the same assessment.

**Transparent**
Every assessment can be traced back to individual rule evaluations.

**Configurable**
Business thresholds and metadata are separated from implementation logic.

**Extensible**
New rules can be added without modifying the core execution engine.

**Testable**
Individual rules and system components can be independently validated.

**Explainable**
Structured rule results provide the basis for human-readable explanations.

**LLM-compatible**
A language model can be introduced as a reporting component without delegating core credit decision logic to the model.
