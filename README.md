# Credit Assessment System

A modular and deterministic rule-based system for the assessment of credit positions.

The project is designed as a prototype for a **transparent, traceable and extensible credit assessment framework**, where business rules are explicitly implemented, independently testable and configurable. The architecture is intentionally separated from any natural-language generation component, allowing an LLM or other reporting layer to be integrated without delegating decision-making logic to the model.

---

## 1. Project Overview

The **Credit Assessment System** evaluates credit positions against a configurable set of financial and sustainability rules.

For each credit position, the system:

1. Loads the configured assessment rules.
2. Discovers and registers the available rule implementations.
3. Instantiates the rules from their configuration.
4. Evaluates each rule against the credit position.
5. Produces a structured `RuleResult` for every configured rule.
6. Aggregates the rule results into an overall assessment status.
7. Optionally generates explanatory comments through a separate comment layer.

The core assessment logic is therefore **deterministic and independent from natural-language generation**.

This separation is a fundamental architectural principle of the project:

> **Rules determine the assessment; the reporting layer explains the assessment.**

---

## 2. Design Principles

The system follows several principles aimed at ensuring maintainability, transparency and testability.

### Deterministic decision logic

Business decisions are implemented through explicit Python rules rather than generated by an LLM.

Given the same position and configuration, the system produces the same assessment.

### Separation of concerns

Each component has a clearly defined responsibility:

* **Rules** evaluate individual financial conditions.
* **Rule Engine** executes rules.
* **Rule Registry** resolves rule identifiers into rule implementations.
* **Configuration Layer** defines which rules are active and their parameters.
* **Assessment Status Calculator** aggregates rule outcomes.
* **Comment Engine** generates explanatory comments.
* **Models** represent domain objects.

### Configuration-driven execution

Rule thresholds, severities and metadata are externalized through configuration rather than hard-coded in the rule engine.

### Extensibility

New rules can be introduced without modifying the core rule engine, discovery mechanism or assessment orchestration.

A new rule is registered through the common `Rule` abstraction and becomes discoverable automatically.

### Traceability

Every rule produces a structured result containing information such as:

* rule identifier;
* rule name;
* category;
* evaluation status;
* evaluated value;
* threshold;
* severity.

This makes the assessment process auditable and explainable.

### Testability

The system is designed around small, independently testable components.

The test suite covers domain models, configuration, individual rules, registration, discovery, services, assessment aggregation and comment generation.

## 5. Rule Abstraction

All business rules inherit from the common `Rule` abstraction.

A rule receives a `RuleConfig` containing its configuration and exposes an `evaluate()` method:

```python
class Rule(ABC):

    _registry: ClassVar[dict[str, type["Rule"]]] = {}

    def __init__(self, config: RuleConfig):
        self.config = config

    @abstractmethod
    def evaluate(
        self,
        position: CreditPosition,
    ) -> RuleResult:
        pass
```

The base class also provides common result-generation functionality and handling for non-evaluable rules.

This ensures that individual rules focus exclusively on their business logic.

---

## 6. Rule Registration

Rules are dynamically registered through a decorator-based registry.

Conceptually:

```python
@Rule.register("R001")
class RevenueGrowthRule(Rule):
    ...
```

The registry maps a stable business identifier to its implementation:

```text
R001 → RevenueGrowthRule
R002 → NegativeEbitdaRule
R003 → EbitdaMarginRule
R004 → PfnToEbitdaRule
R005 → FinancialExpensesToEbitdaRule
R006 → EbitdaInventoryContributionRule
R007 → InterestCoverageRatioRule
```

Duplicate rule identifiers are rejected during registration.

Unknown identifiers are also explicitly rejected when building the rule set.

The rule identifier acts as the stable link between:

```text
Configuration
      │
      ▼
Rule ID
      │
      ├──► Rule implementation
      │
      ├──► Rule configuration
      │
      ├──► Rule tests
      │
      └──► Comment template
```

This provides a consistent mechanism for extending the system.

---

## 7. Dynamic Rule Discovery

The system does not require the central registry to explicitly import every rule implementation.

`discover_rules()` dynamically walks the `src.rules` package and imports rule modules.

Importing a rule module triggers its registration decorator, making the rule available in the registry.

This provides a plug-in-like architecture:

```text
New rule module
       │
       ▼
Package discovery
       │
       ▼
Module import
       │
       ▼
@Rule.register(...)
       │
       ▼
Rule Registry
```

The discovery mechanism deliberately excludes infrastructure modules such as:

* `registry`;
* `discovery`;
* base rule modules.

The discovery process is also designed to be idempotent once modules have already been imported.

As a consequence, adding a new rule does **not** require manually updating a central list of rule classes.

## 8. Rule Construction

The rule registry is responsible for transforming configuration objects into concrete rule instances.

```python
def build_rules(
    configs: list[RuleConfig],
) -> list[Rule]:

    discover_rules()

    rules = []

    for config in configs:
        rule_class = Rule.get_registered_rule(
            config.rule_id
        )
        rules.append(rule_class(config))

    return rules
```

The configuration therefore determines **which rules are instantiated and with which parameters**, while the registry determines **which implementation corresponds to each rule identifier**.

This keeps configuration and implementation decoupled.

---

## 9. Rule Engine

The `RuleEngine` deliberately contains no business-rule logic.

Its responsibility is simply to execute the supplied rules:

```python
class RuleEngine:

    def __init__(self, rules: list[Rule]):
        self.rules = rules

    def evaluate(
        self,
        position: CreditPosition,
    ) -> list[RuleResult]:

        results = []

        for rule in self.rules:
            results.append(
                rule.evaluate(position)
            )

        return results
```

This design makes the engine generic: it does not need to know whether a rule evaluates revenue growth, EBITDA, leverage, interest coverage or another financial indicator.

Therefore, adding a new business rule does not require modifying `RuleEngine`.

## 10. Rule Results

Every rule returns a structured `RuleResult`.

A result contains the information required to understand the outcome of an individual rule evaluation:

```text
RuleResult
├── rule_id
├── rule_name
├── category
├── status
├── value
├── threshold
└── severity
```

Typical rule statuses include:

* `TRIGGERED`
* `NOT_TRIGGERED`
* `NOT_EVALUABLE`

The structured result allows downstream components to operate on rule outcomes without depending on the implementation details of individual rules.

## 11. Assessment Status

The overall assessment is derived from the individual rule results.

The current aggregation logic is:

```text
Triggered rules = 0
        │
        ▼
     NORMAL

Triggered rules = 1
        │
        ▼
    ATTENTION

Triggered rules ≥ 2
        │
        ▼
    CRITICAL
```

The `AssessmentStatusCalculator` is intentionally separated from the `RuleEngine`.

This is important because:

> **Rule evaluation and assessment aggregation are two different responsibilities.**

The rule engine determines what happened at rule level; the status calculator determines the overall assessment.

## 13. Configuration

Rules are configured independently from their implementation.

A configuration entry can define attributes such as:

```text
rule_id
rule_name
category
threshold
severity
```

For example:

```yaml
- rule_id: R007
  rule_name: Interest coverage ratio
  category: profitability
  threshold: 2.0
  severity: MEDIUM
```

The configuration determines whether a rule is part of the active assessment rule set.

This distinction is important:

> **Creating a rule implementation does not automatically mean that the rule is active.**

A rule becomes part of the configured assessment when its corresponding configuration entry is present.

This allows thresholds and metadata to be changed without modifying the rule implementation itself.

The configuration-driven approach supports:

* parameterization;
* reproducibility;
* environment-specific configurations;
* easier validation;
* reduced coupling between code and business parameters.

## 14. Comment and Reporting Layer

The comment system is deliberately separated from the assessment engine.

The intended architecture is:

```text
Credit Position
      │
      ▼
Rule Engine
      │
      ▼
Rule Results
      │
      ▼
Assessment Status
      │
      ▼
Comment / Reporting Layer
```

The comment layer transforms structured assessment results into human-readable explanations.

Each triggered rule can have a corresponding comment template identified by the same rule ID.

For example:

```text
R001 → Revenue deterioration comment
R002 → Negative EBITDA comment
R003 → EBITDA margin comment
R004 → Leverage comment
R005 → Financial expenses / EBITDA comment
R006 → EBITDA inventory contribution comment
R007 → Interest coverage ratio comment
```

This maintains a consistent separation between:

* **decision logic**;
* **structured results**;
* **natural-language explanation**.

This separation is particularly important for future integration with an **LLM-based reporting component**.

The LLM should operate on already-determined results rather than independently deciding whether a credit rule is triggered.

Therefore:

```text
Deterministic layer
        │
        ├── evaluates rules
        ├── determines statuses
        └── determines assessment
                 │
                 ▼
       Natural-language layer
                 │
                 └── explains results
```

This preserves deterministic decision-making while allowing flexible natural-language reporting.

## 15. Extensibility: Adding a New Rule

One of the main architectural goals of the project is that adding a new business rule should be **additive rather than invasive**.

The implementation has been explicitly validated by introducing additional rules without modifying the core orchestration components.

For example, the addition of the `Interest Coverage Ratio` rule followed the same architecture already used by the existing rules.

The workflow is:

```text
1. Create rule implementation
          │
          ▼
2. Register with @Rule.register(...)
          │
          ▼
3. Add configuration to rules.yaml
          │
          ▼
4. Add comment template
          │
          ▼
5. Add unit tests for the rule
          │
          ▼
6. Update/add scenario tests only where
   the new rule changes expected behaviour
          │
          ▼
7. Run complete test suite
```

### Step 1 — Create the rule

The new rule is placed in the appropriate business taxonomy:

```text
src/rules/financial/profitability/interest_coverage_ratio.py
```

It implements the common `Rule` interface.

### Step 2 — Register the rule

The rule is associated with a unique business identifier:

```python
@Rule.register("R007")
class InterestCoverageRatioRule(Rule):
    ...
```

No modification to the central registry is required.

### Step 3 — Add configuration

The corresponding rule is added to the active configuration:

```yaml
- rule_id: R007
  rule_name: Interest coverage ratio
  category: profitability
  threshold: 2.0
  severity: MEDIUM
```

The configuration controls whether the rule participates in the default assessment service.

### Step 4 — Add the comment template

If the rule is intended to generate a human-readable explanation, a template is added using the same rule identifier.

This preserves the mapping:

```text
R007
 │
 ├── Rule implementation
 ├── Rule configuration
 ├── Rule tests
 └── Comment template
```

### Step 5 — Add rule-specific tests

The new rule receives its own test module covering relevant scenarios such as:

* triggered;
* not triggered;
* not evaluable;
* missing inputs;
* boundary conditions;
* custom configuration.

These tests validate the business logic independently from the rest of the system.

### Step 6 — Update scenario tests only when necessary

Service-level tests should validate **behaviour**, rather than the exact number of rules.

For example, this is preferable:

```python
assert len(assessment.rule_results) == len(
    assessment_service.rule_engine.rules
)
```

rather than:

```python
assert len(assessment.rule_results) == 7
```

Likewise, scenario tests should avoid unnecessarily hard-coding every rule identifier when the purpose of the test is to validate general assessment behaviour.

This means that adding a new rule should not automatically require rewriting unrelated tests.

If the new rule changes the expected outcome of a specific scenario, that scenario should be updated accordingly.

### Architectural result

The core orchestration remains unchanged:

```text
RuleEngine
AssessmentService
Rule Discovery
Rule Registry
AssessmentStatusCalculator
```

do not need to be modified merely because a new business rule has been introduced.

This is the practical manifestation of the project's extensibility principle:

> **New business rules are added through extension points rather than changes to the orchestration layer.**

## 16. Testing Strategy

The testing strategy is divided into different levels.

### Rule-level tests

Each individual rule has dedicated tests for its own business logic.

For example:

```text
tests/rules/financial/profitability/
├── test_ebitda_inventory_contribution.py
├── test_financial_expenses_to_ebitda.py
├── test_interest_coverage_ratio.py
└── test_negative_ebitda.py
```

These tests are intentionally specific to the rule.

### Infrastructure tests

The architecture also contains tests for:

* rule registration;
* duplicate identifiers;
* dynamic discovery;
* configuration;
* result generation.

These tests verify the framework rather than individual business rules.

### Service-level tests

Service tests validate the interaction between:

```text
Configuration
      ↓
Rule Discovery
      ↓
Rule Registry
      ↓
Rule Engine
      ↓
Assessment Service
      ↓
Assessment Status
      ↓
Comments
```

These tests should be as configuration-driven as possible.

For example:

```python
assert len(assessment.rule_results) == len(
    service.rule_engine.rules
)
```

is preferable to hard-coding the current number of configured rules.

Similarly, a generic assertion such as:

```python
assert all(
    result.status != RuleStatus.TRIGGERED
    for result in assessment.rule_results
)
```

is preferable to enumerating every rule ID when the scenario is intended to verify that the assessment contains no triggered rules.

This makes the test suite more resilient to future rule additions.

## 17. Test Extensibility Validation

The project uses the addition of new rules as an architectural validation exercise.

A useful extensibility test is:

1. Introduce a new rule.
2. Register it using the existing decorator.
3. Add its configuration.
4. Add its comment template.
5. Add rule-specific tests.
6. Run the entire test suite.
7. Verify that the core engine and orchestration code remain unchanged.

If the complete suite passes after these changes, the architecture has demonstrated that the new rule can be incorporated without modifying the central execution mechanism.

This is more meaningful than simply demonstrating that an individual rule works.

It verifies that the **system-level extension points are functioning correctly**.

## 22. Architectural Boundaries

The project intentionally maintains the following boundaries:

| Component                    | Responsibility                        |
| ---------------------------- | ------------------------------------- |
| `Rule`                       | Common rule abstraction and registry  |
| Individual rules             | Business-rule evaluation              |
| `RuleConfig`                 | Rule parameters and metadata          |
| `RuleConfigLoader`           | Configuration loading                 |
| `RuleConfiguration`          | Configuration source/path definition  |
| `discovery.py`               | Dynamic rule module discovery         |
| `registry.py`                | Rule construction from configuration  |
| `RuleEngine`                 | Rule execution                        |
| `RuleResult`                 | Structured rule outcome               |
| `AssessmentStatusCalculator` | Overall assessment aggregation        |
| `AssessmentService`          | Assessment orchestration              |
| `CommentEngine`              | Human-readable explanation generation |
| LLM layer                    | Optional natural-language reporting   |

Keeping these boundaries explicit reduces coupling and makes the system easier to validate and evolve.

## 23. Architectural Goal

The long-term goal is to provide a credit assessment framework that is:

**Deterministic**
The same inputs and configuration produce the same assessment.

**Transparent**
Every assessment can be traced back to individual rule evaluations.

**Configurable**
Business thresholds and metadata are separated from implementation logic.

**Extensible**
New rules can be added without modifying the core execution engine.

**Testable**
Individual rules and system components can be independently validated.

**Explainable**
Structured rule results provide the basis for human-readable explanations.

**LLM-compatible**
A language model can be introduced as a reporting component without delegating core credit decision logic to the model.

## 25. Architectural Extension Checklist

When introducing a new rule, the practical checklist is:

```text
[ ] Define the business logic
[ ] Create the rule module
[ ] Assign a unique rule ID
[ ] Add @Rule.register(...)
[ ] Add the rule to rules.yaml
[ ] Add/update the CreditPosition input if necessary
[ ] Add the comment template if required
[ ] Add dedicated rule tests
[ ] Update scenario tests only if expected behaviour changes
[ ] Run pytest
[ ] Run linting
[ ] Run coverage
[ ] Verify CI
```

The important distinction is that **not every new rule requires changes to every component**.

For example:

```text
New rule
   │
   ├── Rule implementation       REQUIRED
   ├── Decorator registration    REQUIRED
   ├── Configuration             REQUIRED
   ├── Rule tests                REQUIRED
   │
   ├── Comment template          REQUIRED if comments are generated
   ├── Model change              ONLY if new input data is required
   └── Service test changes      ONLY if scenario expectations change
```

This is the intended extension model of the architecture.
